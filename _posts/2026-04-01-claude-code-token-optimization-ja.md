# Claude Code のトークンを賢く節約する完全ガイド

> 対象：Claude Code CLI、claude.ai Chat、Claude Desktop の全プロダクト
> 出典：Anthropic 公式ドキュメント、コミュニティのベストプラクティス、ヘビーユーザーの知見

---

## なぜすぐに利用上限にぶつかるのか

「メッセージ1通=消費量1単位」だと思っている人が多いが、実際には**メッセージ数と実際の消費量はまったく別物**だ。消費を押し上げる主な要因は次の4つある。

### 長い会話は雪だるま式にコストが膨らむ

もっともよくある落とし穴がこれだ。50ターン続く会話では、メッセージを送るたびに Claude が**会話履歴全体**を読み直す。つまり——

> 長い会話の中の1通は、新規会話の最初の1通より**8〜10倍**のコストがかかる。

同じ会話の中で資料整理や調べものを延々と続けてしまうチームは、まさにこのパターンでクォータを消耗している。

### ファイルアップロード

PDF や Word などの大きなファイルをアップロードするたびに、その内容がそのまま Context Window に入り込み、1回あたりの消費が跳ね上がる。新しい会話のたびに同じファイルを再アップロードしていれば、その分だけ無駄なコストを重ねていることになる。

### モデル選び

| モデル | 相対コスト |
|------|---------|
| Haiku | Sonnet の約30% |
| **Sonnet** | **基準（1倍）** |
| Opus | Sonnet の**3〜5倍** |

資料整理に Opus を使うのは、コンビニに行くのにスポーツカーを出すようなものだ。

### プロダクト間でクォータを共有している

**claude.ai、Claude Code CLI、Claude Desktop は同一のクォータプールを共有している。** Claude Code でガッツリコーディングしたあと claude.ai を開いたら残量がなかった、というのはこのためだ。プールが1つしかない。

## 5時間ローリングウィンドウの仕組み

「5時間ごとに自動リセット」ではなく、**ローリングウィンドウ**という仕組みで動いている。

1. 最初のメッセージを送った瞬間に**ウィンドウのカウントが始まる**
2. そのメッセージが使ったクォータは**送信から5時間後**に解放される
3. メッセージを送らなければ、ウィンドウは無期限に開いたままになる
4. 消費量は**トークンベース**で決まる——単純なメッセージ数ではなく、複雑・長文なメッセージほど多く消費する

**対策**：上限が近づいてきたら、次のメッセージを送る前に5時間の窓が閉じるのを待つ。その待ち時間を使って次のプロンプトを練り込み、新しいウィンドウの1通目で最大の成果を出せるようにするとよい。

## Context Window の構造——見えないコストの正体

トークン最適化を理解するうえで最も核心的な概念がこれだ。

> 「ベストプラクティスの大半は、ある1つの制約に基づいている。Claude の Context Window はすぐに埋まり、埋まるほどパフォーマンスが落ちる、という制約だ。」——公式ドキュメントより

### 200Kトークンの内訳

| 構成要素 | トークン数 | 割合 |
|------|---------|------|
| システムプロンプト＋ツール定義 | 約18,000〜19,000 | 約10% |
| CLAUDE.md（全階層合算） | 2,000〜42,000以上 | 1〜21% |
| MCPサーバーのツール定義 | 変動 | 0〜5% |
| 自動圧縮用の予約領域 | 約33,000〜45,000 | 約17〜23% |
| **実際の作業に使える分** | **約100,000〜145,000** | **約50〜72%** |

**典型的なヘビーユーザーは、最初の1文字を打つ前にすでに50,000〜70,000トークンを使い切っている**——200Kウィンドウの25〜35%にあたる。

### Context のサイズがなぜコストを左右するのか

トークンのコストは Context のサイズに比例して増える。送るメッセージには毎回、会話全体のコンテキストが含まれるからだ。Context が膨らむほど——
- メッセージ1通のコストが上がる
- Claude のパフォーマンスが落ちる
- 早い段階の指示を「忘れる」リスクが増す
- 自動圧縮が発動し、重要な細部が失われる可能性が出てくる

## プロンプトキャッシュの仕組み——効くテクニックと効かないテクニックの分かれ目

### 前方一致という仕組み

プロンプトキャッシュは**前方一致（プレフィックスマッチ）**で動く。新しいリクエストがどこまで既処理内容と一致するかを API が確認する仕組みだ。前方部分のどこか1箇所でも変わると、それ以降のキャッシュはすべて無効になる。

### Claude Code のキャッシュ構造

Claude Code はリクエストを**静的な内容を前に、動的な内容を後ろに**という順で組み立てている。

1. **システムプロンプト**（固定、常にキャッシュされる）
2. **ツール定義**（安定しており、キャッシュされる）
3. **CLAUDE.md の内容**（セッション内では安定、キャッシュされる）
4. **会話メッセージ**（動的で、ターンごとに増える）

### 料金への影響

| トークン種別 | コスト倍率 |
|-----------|---------|
| キャッシュ作成 | 1.25倍 |
| キャッシュ読み込み | **0.1倍** |
| 損益分岐点 | 2ターン目 |

長時間のセッションでは**キャッシュヒット率が90%**に達することもあり、トークン単価が大幅に下がる。

### 実践上のポイント

- **会話の途中で CLAUDE.md を書き換えない**——それ以降のキャッシュがすべて無効になる
- **システム側のコンテキストは安定させる**——CLAUDE.md が安定しているほどキャッシュが効きやすい

## 自動圧縮と手動圧縮

### 自動圧縮が発動する条件

Context Window が容量の約**95%**（残り約25%）に達すると発動する。ただし、多くのヘビーユーザーは**自動圧縮を待たない**ことを勧めている。Agent が重要なコンテキストを失って「暴走」する原因になりかねないからだ。

### `/compact` による手動圧縮

```bash
/compact                              # 基本の圧縮
/compact コード例は残して              # 残す内容を指定
/compact API変更履歴を重点的に残して    # 独自の保持指示
```

CLAUDE.md に圧縮時の指示を書き込んでおくこともできる。
```markdown
# Compact instructions
圧縮する際は、テスト出力とコードの変更点を中心に残してください
```

### `/rewind` ＋要約——狙い撃ちの圧縮

もっとも精密な Context 管理テクニック。

1. `Esc + Esc` を押すか `/rewind` を実行する
2. メッセージのチェックポイントを選ぶ（例：40ターンの会話の中盤あたり）
3. **「Summarize from here」**を選択する
4. そのポイントより前の内容が要約され、それ以降はそのまま保持される

### 圧縮すべきタイミングの目安

| 発動条件 | やるべきこと |
|---------|------|
| Context使用率がおおむね50% | 残す内容を指定して `/compact` を実行 |
| サブタスクを切り替えるとき | 新しい作業を始める前に圧縮 |
| 探索が終わり実装に入るとき | 探索フェーズ分を圧縮 |
| デバッグが終わったあと | 圧縮してから修正に着手 |
| **圧縮を避けるべきタイミング** | 実装中、デバッグ中、複数ファイルのリファクタリング中 |

## CLAUDE.md の最適化——最大の隠れコスト

### 何が問題なのか

CLAUDE.md は**セッション開始時**と**メッセージごとの Context**の両方で毎回読み込まれる。肥大化した CLAUDE.md は、すべてのやり取りに継続的にのしかかる「税金」のようなものだ。

**実例**：ある開発者の CLAUDE.md は、会話1回あたり約42,000トークンを消費していた。最適化後は約2,400トークンまで削減——**94%減**である。

### 公式の推奨

> 「CLAUDE.md は200行以内に収め、本当に必要な情報だけを書くこと。」——公式ドキュメントより

### 書くべきこと・書くべきでないこと

| 書くべきこと | 書くべきでないこと |
|---------|---------|
| Claude が推測できない Bash コマンド | コードを読めば分かること |
| デフォルトと異なるコーディング規約 | 一般的な言語の慣習（Claude はすでに知っている） |
| テストの実行方法と推奨フレームワーク | 詳細な API ドキュメント（リンクに置き換える） |
| リポジトリのルール（ブランチ命名、PRのルール） | 頻繁に変わる情報 |
| プロジェクト固有のアーキテクチャ上の判断 | 長々とした説明やチュートリアル |
| 開発環境特有のクセ | ファイルの一覧的な説明 |
| よくある落とし穴や非自明な挙動 | 「きれいなコードを書く」のような自明なルール |

### 最適化の手順

1. **`/context` で棚卸しする**：CLAUDE.md が実際に何トークン消費しているかを確認する
2. **1行ごとに問う**：この行を消したら Claude がミスをするか？しないなら消す
3. **インラインではなく `@` 参照にする**：`@docs/testing.md` として必要なときだけ読み込ませる
4. **特定のワークフローは Skills に移す**
5. **短く保つ**：段落ではなく箇条書きにする
6. **定期的に整理する**：コードと同じ感覚で CLAUDE.md をメンテナンスする

### CLAUDE.md の階層（どれもトークンコストが発生する）

| 場所 | 適用範囲 | 常に読み込まれるか |
|------|-------|-------------|
| `~/.claude/CLAUDE.md` | 全プロジェクト・全セッション | はい |
| `./CLAUDE.md`（プロジェクトルート） | そのプロジェクトの全セッション | はい |
| 親ディレクトリ | monorepo 構成の場合 | はい |
| サブディレクトリ | そのサブディレクトリで作業するとき | 必要に応じて |

**注意**：グローバルの CLAUDE.md とプロジェクトの CLAUDE.md は同時に読み込まれる。両方を最適化する必要がある。

## Skills による必要時読み込み——CLAUDE.md 肥大化への処方箋

### アーキテクチャの原理

Skills（`.claude/skills/*/SKILL.md`）は**段階的な読み込み**方式を採る。

1. 起動時に読み込まれるのは、各 Skill の**名前と説明**（メタデータ）だけ
2. その Skill が実際に関係してきたときに初めて、Claude が全文を読む
3. Skill が参照する付随ファイルも必要になったときだけ読み込まれる

つまり PR レビューやデータベースマイグレーション、デプロイの手順といった専用の指示は、関係のない作業をしている間は**トークンを一切消費しない**。

### 具体的な削減効果

| 方式 | セッションあたりトークン数 | 削減率 |
|------|---------------|------|
| すべて CLAUDE.md に書く | 約42,000 | 基準 |
| モジュール化した Skills 構成 | 約2,400（常時読み込み分） | **94%** |

### 移行の手順

1. CLAUDE.md の中から、特定のワークフローでしか使わない記述のかたまりを見つける
2. Skill 用ディレクトリを作る：`.claude/skills/<ワークフロー名>/SKILL.md`
3. 該当する内容を SKILL.md に移す
4. CLAUDE.md から該当箇所を削除する
5. 必要なら CLAUDE.md に一言だけ添える。「デプロイ作業は `/deploy` を使用」など

## Subagent のトークン経済学

### 仕組み

Subagent は**独立した Context Window** の中で動作し、メイン会話には**要約**だけを返す。Context 節約のための最強の手段の1つだ。

### Subagent を使う価値があるのはどんなとき

| タスク | メイン Context で直接実行 | Subagent | 推奨 |
|------|---------------------|--------|------|
| ファイル1〜2個を読む | オーバーヘッドは低い | 起動コストのほうが高い | **直接実行** |
| ファイル3個以上の探索 | Context が汚染されやすい | 要約だけが返る | **Subagent** |
| テストの実行 | 冗長な出力が Context を埋める | 出力は Subagent 側に留まる | **Subagent** |
| コードレビュー | 自分が書いたコードにはバイアスがかかる | まっさらな Context でバイアスなし | **Subagent** |
| ドキュメントの取得 | 大量の内容が流れ込む | フィルタ済みの要約だけが返る | **Subagent** |

### Subagent の起動コスト

Subagent には**5,000〜15,000トークン**の起動オーバーヘッドがある（CLAUDE.md の読み込みやロールの構築など）。単純なタスクに Subagent を使うべきではない理由はここにある。

### Subagent のモデル設定

`~/.claude/settings.json` で以下のように設定する。
```json
{
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku"
  }
}
```

Haiku は Sonnet より**約80%安い**ため、ファイル読み込み・探索・テスト実行といった用途には十分すぎるほどだ。

### Agent Teams の「7倍」警告

Agent Teams は標準的なセッションの**約7倍**のトークンを消費する。各 teammate がそれぞれ独立した完全な Context Window を維持するためだ。推奨事項は次の通り。
- teammate の実行には Opus ではなく Sonnet を使う
- チームは小規模に保つ（teammate は最大2〜3人まで）
- 作業後は片付ける——アクティブな teammate はアイドル状態でもトークンを消費し続ける

## Claude Code と claude.ai——トークン消費の違い

### 共有クォータプール

**すべての Claude プロダクトは同じクォータプールを共有している。** Pro/Max のクォータは、どのインターフェースを使っても同じ枠から減っていく。

### なぜ Claude Code のほうが消費が多いのか

| 要因 | claude.ai Chat | Claude Code CLI |
|------|---------------|----------------|
| システムプロンプト | 最小限 | 約18,000〜19,000トークン |
| CLAUDE.md | なし | 2,000〜42,000トークン以上 |
| MCPサーバー | なし | サーバーごとにオーバーヘッドが発生 |
| ツール呼び出し | なし | 呼び出すたびに追加トークンが発生 |
| ファイル読み込み | 手動でペースト | 自動で、大量のファイルを読むこともある |
| マルチステップのタスク | 単発のやり取り | Agent ループ：1タスクに複数ターン |
| Subagent | 非対応 | Subagentごとに新しい Context が作られる |

### 実践上のアドバイス

コーディングと関係のない単純な質問には——
- Claude Code ではなく claude.ai のチャットを使う
- あるいは Claude Code の中で `/btw` を使う——**会話履歴には残らず**、Context コストはゼロ

## 具体的な節約テクニック12選（効果の大きい順）

### 第1グループ：効果が最も大きい（1項目あたり30〜50%の削減）

**1. `.claudeignore` ファイル——30〜40%削減**

プロジェクトルートに `.claudeignore` を作り、Claude が読む必要のないディレクトリを除外する。

```
node_modules/
.next/
build/
dist/
*.log
*.lock
coverage/
.git/
```

Next.js プロジェクトでは `.next/` を除外するだけで Context を30〜40%削減できる。

**2. タスクの切り替え時は `/clear`——無駄の積み重ねを防ぐ**

前のタスクの古い Context は、そのあとのメッセージすべてでトークンを無駄に消費し続ける。「タスク完了 → `/clear` → 次のタスク開始」を習慣にするとよい。

**3. 複雑なタスクには Plan Mode——20〜30%削減**

`Shift+Tab` で Plan Mode に入る。Claude は探索と計画だけを行い、変更を実行しないため、コストのかかる試行錯誤の反復を避けられる。3ファイル以上にまたがるタスクでとくに効果が大きい。

### 第2グループ：効果は中程度（1項目あたり10〜25%の削減）

**4. プロンプトの精度——15〜25%削減**

悪い例：「ログイン機能を追加して」

良い例：「`src/auth/login.ts` にメール／パスワードでのログインを追加してほしい。`src/auth/register.ts` の `AuthService` のパターンを踏襲すること。テストは `tests/auth/login.test.ts` に書くこと」

精度の高いプロンプトなら一発で通るが、曖昧なままだと4往復の確認が必要になる。

**5. Context 使用率50%で `/compact`を実行する——10〜15%削減**

95%まで待って自動圧縮に任せるのではなく、次のタイミングで自分から実行する。
- 探索が終わり実装に入る前
- マイルストーンを達成したあと
- 大きく Context を切り替える前

**6. CLAUDE.md のスリム化——5〜10%削減（肥大化している場合はもっと大きい）**

600行以上あるものを200行以内に減らす。専用のワークフローは Skills に移す。

**7. MCPサーバーの管理——5〜10%削減**

接続している MCPサーバーはそれぞれ、メッセージごとにツール定義を追加する。デフォルトではどのサーバーにも接続せず、必要になったときだけ追加する。`/mcp` で棚卸しするとよい。

### 第3グループ：効率の乗数になるもの

**8. モデル選び**

- **Sonnet**：コーディングタスクの約80%はこれで十分。デフォルトの選択肢。
- **Haiku**：Subagent、探索、テスト実行に。80%安い。
- **Opus**：複雑なアーキテクチャ設計や多段階の推論にのみ使う。`/model` で切り替える。

**9. Extended Thinking の制御**

デフォルトの思考予算は数万トークンに達することがある。単純なタスクでは次のように制限する。

```json
{ "env": { "MAX_THINKING_TOKENS": "10000" } }
```

`Alt+T`（Mac は `Option+T`）で切り替えられる。31,999から10,000まで下げると、目に見えない推論コストを約70%削減できる。

**10. 脱線質問には `/btw`——Contextコストゼロ**

2026年3月に導入されたコマンド。会話履歴に残らないオーバーレイの中で質問できる。

```
/btw TypeScriptのジェネリクスの構文って何だっけ？
```

構文の確認、API のちょっとした確認、素早い疑問解消に向いている。脱線質問1つで最大50%節約できる。

**11. 冗長な作業は Subagent に任せる**

テストの実行、ドキュメントの取得、ログ解析は Subagent に委任する。冗長な出力は Subagent 側の Context に留まり、要約だけが返ってくる。

**12. Hooks による前処理**

Claude がデータを目にする前に Hooks でフィルタリングする。何万行ものログを、重要な数百行だけに絞り込むといった使い方ができる。

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "~/.claude/hooks/filter-test-output.sh"
      }]
    }]
  }
}
```

## 上級者向けの戦略

### 戦略1：セッションを構造化して管理する

Git のブランチのように Session を扱い、ワークフローごとに永続的な Context を分ける。

```bash
/rename oauth-migration      # Session に名前を付ける
claude --resume               # 特定の Session を再開する
claude --continue             # 直近の Session を続ける
```

### 戦略2：書き手／レビュアー方式

並行する2つの Session を使い、自己レビューによるバイアスを避ける。

| Session A（書き手） | Session B（レビュアー） |
|----|----|
| 「API エンドポイントのレートリミッターを実装して」 | （待機） |
| （完了） | 「`@src/middleware/rateLimiter.ts` のレートリミッターをレビューして。エッジケースと競合状態を確認して」 |
| 「レビューの指摘に対応：[Bのアウトプットを貼り付け]」 | （完了） |

まっさらな Context で行うので、バイアスのないコードレビューになる。

### 戦略3：大規模移行の Fan-Out

```bash
for file in $(cat files.txt); do
  claude -p "$file を React から Vue に移行して。結果は OK か FAIL で返して" \
    --allowedTools "Edit,Bash(git commit *)"
done
```

非対話モード（`-p`）は、対話型の Session よりも消費トークンが明確に少ない。

### 戦略4：MCP よりも CLI ツール

`gh`、`aws`、`gcloud`、`sentry-cli` などの CLI ツールは、外部サービスとやり取りするうえで最も Context 効率のよい手段だ。MCPサーバーのように、ツール一覧のオーバーヘッドが毎回上乗せされることがない。

### 戦略5：引き継ぎドキュメント（Handoff）

複数の Session にまたがる複雑な作業では、新しい Session を始める前に次を行う。

1. Claude に、進捗・決定事項・次のステップをまとめた引き継ぎドキュメントを作らせる
2. `/clear` で Session をクリアする
3. 新しい Session を「`@handoff.md` を読んで作業を続けて」で開始する

決定事項だけを引き継ぎ、古い Context は持ち越さずに済む。

### 戦略6：Context を継続的に監視する

`/context` を定期的に実行して、何が空間を消費しているかを確認する。使用状況を常に把握していること自体が、自然と効率的な振る舞いを促してくれる。

### 戦略7：オフピーク時間帯に作業する

Claude Code の作業が集中する時間帯を**オフピーク**にずらす（平日の太平洋時間5〜11時を避ける）と、次のような恩恵が得られる。

- 枠に余裕ができる（Pro：ピーク時35〜40通に対し50〜60通以上）
- スロットリングが少なくなる
- 週あたりの実質利用時間が30〜40%増える

## 利用シーン別の具体的なアドバイス

### Claude Code でのコーディング

| 施策 | 説明 |
|------|------|
| こまめに `/compact` | Context を圧縮し、Session あたりの消費を抑える |
| 不要なファイルを Context に入れない | CLAUDE.md と `.claudeignore` で範囲を絞る |
| まとまった作業は一度に指示する | 「この3つを全部やって」は3回に分けるより効率的 |
| タスクを正確に説明する | ファイルパス、参照すべきパターン、テストの置き場所を含める |
| 探索と実装をフェーズで分ける | 探索が終わったら圧縮してからコードを書き始める |

### claude.ai Chat / Cowork

| 施策 | 説明 |
|------|------|
| 会話を長引かせない | 同じ会話が長くなるほど、1通あたりの消費が増える。適度に新しい会話を始める |
| ドキュメントは Project に入れる | Project は RAG を使い、関連する内容だけを読み込む。毎回アップロードするより大幅に節約できる |
| 使わないツールはオフにする | Web Search、Research、MCP コネクタは多くのトークンを消費する。使わないときは切っておく |
| Extended Thinking は必要なときだけ | 単純なタスクでは Extended Thinking をオフにして Context の空間を空ける |
| Cowork の共有クォータに注意する | Cowork と Chat はクォータを共有しているので、不要な並行利用は避ける |

## モデル選びの戦略

**学習フェーズ**でも**日常の利用**でも、いちばん見落とされがちな最適化ポイントがここだ。

| タスクの種類 | 推奨モデル | 理由 |
|---------|---------|------|
| 資料整理・要約 | Sonnet | Opus の3〜5分の1のコストで、品質は十分 |
| 資料・プレゼン生成 | Sonnet | 同上 |
| 単純なコーディング・リファクタリング | Sonnet | デフォルト設定で問題ない |
| ファイル探索・テスト | Haiku | 最安で、これで十分 |
| 複雑な推論・戦略立案 | Opus | Opus を使うべきはここだけ |
| Subagent | Haiku | コストを80%削減できる |

**切り替え方法**：Claude Code の中で `/model` コマンドを使えば、いつでも切り替えられる。

### 覚えておきたいコマンド

| コマンド | 用途 | トークンへの影響 |
|------|------|-----------|
| `/clear` | タスクの節目で Context をリセット | 無駄の積み重ねを防ぐ |
| `/compact [指示]` | 会話を圧縮する | 10〜15%節約 |
| `/btw` | 脱線質問、Context コストゼロ | 脱線質問1つで最大50%節約 |
| `/context` | 何がトークンを消費しているか確認する | 診断用 |
| `/cost` | 現在の Session のトークン消費額（API ユーザー向け） | 診断用 |
| `/stats` | 利用パターンの確認（サブスクリプションユーザー向け） | 診断用 |

| `/rewind` ＋要約 | 会話の一部だけを圧縮する | Context をピンポイントで整理 |
| `Esc` | 実行中の処理を中断する | 誤った方向への浪費を防ぐ |
| `Esc + Esc` | 巻き戻しメニューを開く | チェックポイントに戻る |

### セルフチェックリスト

- 同じ長い会話の中で質問を延々と積み重ねていないか？（高消費の原因）
- 新しい会話のたびに同じドキュメントを再アップロードしていないか？（重複消費）
- どのモデルを使っているか？Sonnet で足りる作業に Opus を使っていないか？
- Cowork と Chat を同時に開いていないか？（クォータを共有している）
- CLAUDE.md は何行あるか？200行を超えていないか？
- `.claudeignore` ファイルは用意してあるか？
- MCPサーバーはいくつ接続しているか？不要なものはないか？
